# 脚手架架构与优化分析

本文档基于对当前仓库的深度分析，列出**除测试之外**在整体架构与脚手架上建议的优化点，便于后续按优先级实施。

---

## 一、架构层面优化

### 1.1 infra / domain 边界违规（高优先级）

**现状**：

- `libs/infra/shared-services/file-storage/` 中的 `bucket-resolver.ts`、`file-storage.module.ts` 通过 `@app/services/ip-info` 引用 **domain 层**的 `IpInfoService`。
- tsconfig 中 `@app/services/*` 指向 `libs/domain/services/*`。
- 《业务与基础设施拆分方案》规定：**infra 不得依赖 domain**。

**根因**：`IpInfoService` 依赖 `CountryCodeService`（domain/db），因此被放在 domain/services；而 file-storage（infra）又需要“按 IP 解析地域”等能力，导致 infra 依赖 domain。

**建议**：

1. **拆分 IP 能力**：
   - 在 **infra** 新增 `IpInfoClient`（或 `shared-services/ip-info`）：仅负责调用 ipinfo.io API + Redis 缓存，不依赖 CountryCode。
   - **domain** 保留 `IpInfoService`：组合 IpInfoClient + CountryCodeService，提供“国家/大洲/时区”等业务增强。
2. **file-storage 只依赖 infra**：bucket-resolver、file-storage.module 改为依赖 infra 的 IpInfoClient（或 infra 的 ip-info 服务），不再引用 `@app/services/ip-info`。
3. **可选**：在 CI 或 ESLint 中增加规则，禁止 `libs/infra/**` 下文件 import `libs/domain/**`。

---

### 1.2 AppModule 重复注册 WinstonModule（中优先级）

**现状**：`apps/api/src/app.module.ts` 中 `WinstonModule.forRootAsync` 出现两次（约 58–66 行与 163–171 行），配置相同，属于重复注册。

**建议**：删除其中一处，只保留一次 `WinstonModule.forRootAsync`。

---

### 1.3 Uploader Controller 违反 Zod-first（中优先级）

**现状**：`apps/api/src/modules/uploader/uploader.controller.ts` 中多处使用 `body as any`（如 getPrivateThumbToken、initMultipart、getPrivateToken、abort、complete 等），将 ts-rest 已校验的 body 强制为 any，违反“Zod-first、禁止手动类型断言”的规范。

**建议**：移除 `body as any`，直接使用 `body`。tsRestHandler 会根据 contract 的 body schema 推断类型，无需断言；若个别字段需扩展，使用 contract 中对应 schema 的 `z.infer` 或扩展 schema，而非 any。

---

### 1.4 TypeScript 严格模式关闭（中优先级）

**现状**：`apps/api/tsconfig.json` 中 `strict`、`strictNullChecks`、`noImplicitAny` 等均为 `false`，不利于长期类型安全与重构。

**建议**：在文档或 README 中明确“建议新模块启用严格模式”；或先在 api 下新建 `tsconfig.strict.json` 继承现有配置并开启严格选项，逐步在部分 libs 上启用，最终统一到严格模式。

---

### 1.5 其它类型安全与规范（低～中优先级）

- **libs 中的 `as any`**：如 sms.service、sms.factory、openspeech.client、auth.guard、streaming-asr-session.guard、request.middleware、rate-limit.interceptor、http.exception 等，在合适处用明确类型或 `unknown` + 类型收窄替代，减少 any。
- **system-health**：直接使用 `this.prisma.write` 已有 eslint-disable，属于健康检查特例，可接受；若希望 infra 更“纯”，可抽象为“健康检查接口”，由上层注入实现。
- **file-storage README**：示例中仍写 `@app/services/file-storage`，实际应统一为 `@app/shared-services/file-storage`，避免误导。

---

## 二、脚手架层面优化

### 2.1 规范文档缺失（高优先级）

**现状**：`.cursorrules` 与 `CLAUDE.md` 中引用了多份“必读”规范文档，但在当前仓库中**不存在**：

| 引用路径 | 说明 |
|----------|------|
| `apps/web/docs/代码质量与类型定义规范.md` | 前端类型与代码质量规范 |
| `apps/web/docs/前端架构与交互优化方案.md` | 前端架构与性能方案 |
| `apps/api/docs/架构分层与事务管理方案-new.md` | 后端分层与事务 |
| `apps/api/docs/API版本兼容方案-统一设计.md` | API 版本设计 |
| `docs/ts-rest_Zod-first_REST_协议框架设计方案.md` | ts-rest + Zod 设计 |

当前仅有：

- `apps/api/docs/业务与基础设施拆分方案.md`
- `docs/脚手架说明.md`、`docs/发布到npm.md`

**影响**：基于脚手架创建的新项目会带着指向“不存在文件”的规则，影响 AI 与人工查阅。

**建议**（任选或组合）：

1. **补齐占位文档**：在脚手架中新增上述路径的占位文档（可简短），说明“本规范在业务项目中按需完善”，并保留与 .cursorrules 一致的目录结构。
2. **精简引用**：在 .cursorrules/CLAUDE 中改为“若存在则阅读”，或仅保留脚手架内已有的文档路径（如业务与基础设施拆分方案），其余改为“参考业务项目文档”的说明。
3. **集中文档目录**：在根目录 `docs/` 下增加 `architecture/`、`frontend/`、`api/` 等子目录，把架构、前端、API 相关规范集中放一份精简版，.cursorrules 只引用这些路径。

---

### 2.2 前端 docs 目录缺失（中优先级）

**现状**：`apps/web/docs/` 不存在，而规范中多处引用 `apps/web/docs/` 下文件。

**建议**：若采用“占位文档”方案，则创建 `apps/web/docs/`，并放入占位或精简版《代码质量与类型定义规范》《前端架构与交互优化方案》；若采用“精简引用”方案，则从 .cursorrules 中移除或改写对 `apps/web/docs/` 的硬编码路径。

---

### 2.3 create-dofe-ai 与初始化流程（中优先级）

**现状**：

- `scripts/export-scaffold-for-create.js` 仅按 `git ls-files` 复制到 `packages/create-dofe-ai/template/`，未做“脚手架专用”的二次处理（如占位符替换、.git 排除等）。
- README/脚手架说明中已说明可运行 `node scripts/init-project.js` 做交互式配置。

**建议**：

1. 在生成项目的 README 或首次打开说明中，明确推荐步骤：安装依赖 → 配置 `.env` →（可选）运行 `node scripts/init-project.js` → `pnpm db:generate` → `pnpm dev`。
2. 若需支持“项目名/包名”等占位符替换，可在 export 或 create 的 CLI 中增加一步替换逻辑，避免用户手动改多处。
3. 在 `create-dofe-ai` 的 README 中注明：模板来自 `pnpm run export-scaffold`，以及发布前需先执行 export。

---

### 2.4 README / 文档一致性（低优先级）

- **根 README**：与 `docs/脚手架说明.md` 在“排除项”“使用方式”上保持一致，避免两处说法冲突。
- **file-storage**：README 中示例统一使用 `@app/shared-services/file-storage`，与代码一致。
- **环境变量**：根 README 与 `apps/api/.env.example`、`apps/web/.env.example` 列表一致，必要时在 README 中直接引用 “See apps/api/.env.example” 等。

---

### 2.5 脚本与工具链（低优先级）

- **init-project.js**：可增强“是否存在 .env”“端口是否冲突”等检查，并在完成后提示下一步命令（如 `pnpm db:generate`、`pnpm dev`）。
- **turbo.json**：当前已包含 build、lint、dev、type-check、test、db:* 等，若后续增加 lint:fix、format 等，可在根 package.json 与 turbo 中一并补齐，保持脚本命名一致。

---

## 三、优化项汇总与建议优先级

| 类别     | 优化项                         | 优先级 | 说明 |
|----------|--------------------------------|--------|------|
| 架构     | infra 不依赖 domain（ip-info 拆分） | 高     | 恢复边界，便于复用与测试 |
| 架构     | 移除 AppModule 重复 WinstonModule | 中     | 避免重复初始化 |
| 架构     | Uploader 去掉 body as any，Zod-first | 中     | 符合项目规范 |
| 架构     | TypeScript 逐步开启严格模式    | 中     | 提升类型安全 |
| 架构     | libs 内 as any 逐步替换、file-storage README 统一 | 低     | 长期可维护性 |
| 脚手架   | 规范文档缺失（占位或精简引用） | 高     | 规则与文档一致 |
| 脚手架   | 前端 docs 目录与引用           | 中     | 与规范引用一致 |
| 脚手架   | create-scaffold 与 init 流程说明/增强 | 中     | 新项目上手更清晰 |
| 脚手架   | README/文档一致性              | 低     | 减少误导 |

---

## 四、实施顺序建议

1. **先做高优先级**：infra/domain 边界（ip-info 拆分）+ 规范文档（占位或精简引用），保证架构边界与 AI/人工查阅体验。
2. **再做中优先级**：去掉重复 WinstonModule、Uploader Zod-first、TS 严格模式规划、前端 docs、create/init 说明。
3. **最后做低优先级**：README 与示例统一、libs 中 as any 逐步替换、init-project 增强等。

以上为除测试外，在整体架构与脚手架上建议的优化方向与优先级；具体实施时可按需拆成 issue 或任务列表逐步落地。
