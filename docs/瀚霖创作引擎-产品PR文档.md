## 1. 产品概述

### 1.1 一句话定位

以多 Agent 架构驱动的「小说 + 剧本」双文体创作大模型与创作平台 —— 既能一句话全自动成书/成剧，也支持创作者在任意节点介入调校。

### 1.2 产品理念

- **AI 主导生成，人类主导审美**：速度、记忆、体力活交给模型；立意、审美、最终裁决交给作者。
- **协同而非替代**：每个 Agent 节点都对人类开放编辑权限，任何中间产物可见、可改、可回滚。
- **长篇小说/剧本是「状态工程」**：好作品的关键不是单次生成质量，而是跨数十万字的角色、设定、伏笔、时间线的一致性管理。

### 1.3 产品边界

- **做**：小说（网文/出版向中长篇/短篇）、剧本（电影、电视剧、话剧、广播剧等标准剧本文体）的创作、改编、评审、修订全流程。
- **不做**：视频生成、分镜成片、拍摄制作等下游环节（仅输出可供下游使用的标准分镜/剧本文件）。

### 1.4 价值主张

| 对象 | 价值 |
|---|---|
| 个人作者 | 日更提速 5–10 倍；卡文救场；长篇不烂尾、不崩设定 |
| 编剧/工作室 | 从梗概到标准剧本的周期从月级压缩到天级；评审意见即时可得 |
| 机构/版权方 | 批量评估稿件、小说改编剧本的成本数量级下降 |

### 1.5 版本口径与近期产品策略

本文档同时包含**产品愿景**与**近期交付规格**，两者必须分开阅读：

| 口径 | 含义 | 当前状态 |
|---|---|---|
| 已具备基线 | Next.js 创作入口、NestJS Studio API、受控 Python Runtime 和架构/目录生成的首条垂直切片 | 已实现首条生成路径；作品持久化、章节、事实与版本待扩展 |
| M0 小说闭环收敛 | 在现有 Web/API 基础上交付可恢复、可审计、可人工裁决的单人小说创作闭环 | 本文定义的近期研发范围 |
| M1 小说内测 | 面向受邀作者的作品级工作台与长篇稳定性验证 | M0 验收后启动 |
| M2 及以后 | 剧本、改编、协作、开放平台与商业化能力 | 仅作方向，不占用 M0/M1 排期 |

**近期决策**：先把“作者能够稳定完成一部小说”做成可用闭环，再扩展为“全自动成书/成剧平台”。M0/M1 不以自训练底座模型、全自动百万字生成、剧本线、团队协作或 Open API 作为上线前置条件；这些能力保留在后续路线图，避免因范围过大使核心体验无法验收。

## 2. 目标用户与核心场景

### 2.1 用户分层

| 层级 | 画像 | 付费意愿 | 核心诉求 |
|---|---|---|---|
| U1 网文作者 | 兼职/全职写手，平台连载 | 中（订阅） | 大纲、续写、扩写、日更字数、不崩设定 |
| U2 职业编剧 | 影视/话剧编剧，项目制 | 高（席位/项目） | 结构搭建、分场、对白打磨、多轮改稿管理 |
| U3 工作室/制作公司 | 批量产出、多人协作 | 高（B 端合同） | 标准化流程、审稿流、权限、API |
| U4 文学爱好者 | 零基础新手 | 低（免费转付费） | 一句话成书、模板引导、低门槛 |
| U5 版权/出版机构 | IP 评估与改编 | 高（项目制） | 稿件评估、改编可行性、小说转剧本 |

### 2.2 核心场景剧本（User Journey）

**场景 1：一句话全自动成书（U4/U1）**
输入「写一部东方玄幻，主角从边陲小城起步」→ 引擎自动完成世界观、角色、分卷大纲 → 逐章写作 → 弧级评审 → 自动重写 → 输出完整书稿 + 体检报告。

**场景 2：人机协同连载（U1）**
作者提供已有 30 章存稿 → 引擎解析建立事实层 → 每日按大纲续写新章 → 作者在线逐段调校 → 一键校验全书一致性。

**场景 3：剧本项目制创作（U2）**
编剧输入故事梗概与人物小传 → 生成分幕/分场大纲 → 逐场生成标准格式剧本 → 评审 Agent 输出结构/节奏/对白报告 → 编剧批注改稿，AI 按批注重写并维护版本树。

**场景 4：小说改编剧本（U5/U3）**
导入长篇小说 → 自动提炼主线、人物关系、名场面 → 生成分集/分幕改编方案（含取舍说明）→ 输出标准剧本初稿。

## 3. 产品总体架构

```
┌────────────────────────────────────────────────────┐
│  H 层 创作者工作台（Web / 客户端）                  │
│  编辑器 · 设定面板 · 评审报告 · 版本管理 · 协作空间  │
├────────────────────────────────────────────────────┤
│  B 层 多智能体协同系统                              │
│  总调度 │ 架构师 │ 写手 │ 评审主编 │ 剧本师 │        │
│  改编师 │ 调研员 │ 合规官 │ 润色师                  │
├────────────────────────────────────────────────────┤
│  C 层 状态化记忆系统（事实层）                      │
│  角色快照 │ 设定集 │ 伏笔账本 │ 时间线 │ 摘要树      │
├────────────────────────────────────────────────────┤
│  A 层 底座大模型                                    │
│  创作微调模型 │ 评审模型 │ 通用底座 │ 嵌入/检索      │
├────────────────────────────────────────────────────┤
│  I 层 合规与安全（贯穿全栈）                        │
└────────────────────────────────────────────────────┘
```

**关键设计原则**：
1. **事实层唯一可信源**：所有 Agent 不直接依赖上下文窗口记忆，而是读写 C 层结构化事实库，从根本上解决长篇漂移。
2. **规划-写作-评审分离**：生成者与评判者必须是不同 Agent（可使用不同模型），避免自我背书。
3. **每个节点可介入**：任何 Agent 的中间产物（大纲、角色卡、章节、批注）均可被人类修改，修改后自动触发下游一致性传播。

### 3.1 关键数据流剖析：写一章的完整时序

以「写手 Agent 写第 58 章」为例，说明各层如何协同（这是理解全系统设计的最小完整样本）：

| 步骤 | 执行者 | 动作 | 读取 | 写入 |
|---|---|---|---|---|
| 1 | B1 总调度 | 判定第 57 章已提交且通过评审，派发第 58 章任务 | 任务状态机、指南针 | 任务队列 |
| 2 | B3 写手 | 加载上下文：前情摘要树（卷/弧/近 3 章）、活跃伏笔 5 条、出场角色快照 4 份、文风卡 | C1/C3/C5/C6/C8 | — |
| 3 | B3 写手 | 回读第 56–57 章原文末段，校准语气与节奏 | 章节库 | — |
| 4 | B3 写手 | 规划本章：目标=揭开叛徒身份；冲突=师徒对峙；情绪曲线=压抑→爆发；章末钩子=危机型 | C5 大纲 | 本章计划 |
| 5 | B3 写手 | 成稿 3800 字 | 以上全部 | 章节草稿 |
| 6 | B3 写手 | 一致性自检：对照事实层校验 23 项（角色在场性、能力边界、时间推进、物品归属…） | C1/C2/C4 | 自检报告 |
| 7 | B8 合规官 | 过程闸扫描本章 | I1 规则库 | 合规记录 |
| 8 | B3 写手 | 提交终稿 + 事实增量：新伏笔 1 条（埋设）、旧伏笔推进 1 条、角色 A 受伤状态变更、时间 +2 天 | — | C1/C3/C4/C9 |
| 9 | B1 总调度 | 登记弧进度；若本章为弧末章，触发 B4 弧级评审 | 指南针 | 任务状态机 |

**人类介入点**：步骤 4（改本章计划）、步骤 5 后（改正文）、步骤 8 后（驳回事实增量）——任何介入都会使下游状态自动失效并重排。

### 3.2 运行架构与服务边界（M0）

```text
浏览器
  │  HTTPS / ts-rest（仅公开契约）
  ▼
Next.js Web
  │  登录态、页面渲染、React Query、任务状态展示
  ▼
NestJS API
  ├─ 认证、用户归属、RBAC、审计、公开 REST/SSE 契约
  ├─ Project / Chapter / Fact / Run 领域数据与事务
  ├─ 调用 Python Runtime 的内部客户端
  └─ PostgreSQL / Redis / RabbitMQ
       │  内部 HTTP + x-runtime-secret；浏览器不可访问
       ▼
Python Runtime（FastAPI）
  ├─ LLM 调用、提示词组装、架构/目录/章节/审校执行
  ├─ 检索与文件产物适配
  └─ 执行工作区与计算日志
```

| 层 | 唯一职责 | 不得承担的职责 |
|---|---|---|
| Next.js | 呈现作品、收集作者输入、显示任务/错误/版本；只调用公开 NestJS 契约 | 直连 Python、保存模型密钥、判定授权、维护事实真相 |
| NestJS | 公开 API、身份与资源归属、领域状态机、持久化、审计、幂等、任务编排和错误语义 | 在 Controller/Service 内拼接创作提示词或直接执行 LLM 调用 |
| Python Runtime | 受控长任务、模型/检索适配、流式生成、执行进度和产物提取 | 对浏览器开放端口、信任客户端 user ID、决定业务权限或持有公开 API 契约 |

当前首条链路为：`POST /studio/projects` 由 NestJS 接收并创建生成任务，内部转发给 Python Runtime 的 `POST /v1/generation-jobs`；Web 通过 `GET /studio/jobs/:jobId` 查询自己拥有的任务。后续所有章节、事实、评审和导出能力必须沿用这个边界，而非新建浏览器到 Python 的直连。

## 5. B 层：多智能体协同系统（核心）

### 5.1 B1 总调度 Agent（Coordinator）｜ **P0**

- **职责**：承接用户需求，驱动全流程闭环：需求澄清 → 规划 → 写作 → 评审 → 重写 → 成稿；管理断点续跑与任务状态机。
- **输入**：一句话需求 / 共创规划确认稿 / 存稿文件。
- **输出**：任务计划、各 Agent 调用序列、最终成品包。
- **关键行为**：
  - 基于事实层状态决定下一步调用哪个 Agent，而非固定流水线（例如评审不通过自动回退写手）。
  - 支持暂停、恢复、从任意章节重跑。
  - 人类介入后自动重排后续计划。
- **验收**：一句话输入到成稿全程零人工干预可跑通；中断恢复后状态零丢失。

### 5.2 B2 架构师 Agent（Architect）｜ **P0**

- **职责**：把需求转化为可执行的创作蓝图，并负责长篇的滚动规划。
- **产出物**：
  1. **作品圣经（Story Bible）**：世界观、主题立意、基调、核心冲突；
  2. **角色体系**：主角/配角/反派的人物小传、动机、弧光、关系图谱；
  3. **指南针（Compass）**：终局方向 + 活跃长线清单 + 规模估计（总章数/总集数区间）；
  4. **骨架大纲**：卷/幕级骨架弧（仅目标 + 预估长度），到时再展开；
  5. **详细大纲**：当前卷/幕的章节/场景级细纲。
- **滚动规划机制**：每完成一卷/一幕，基于已写内容的摘要树和角色快照，自主展开下一段详细规划；故事方向允许随创作演化，但演化必须登记变更日志。
- **验收**：从一句话需求推导的蓝图经人类确认率 ≥ 60% 可直接开写；跨卷规划与前文摘要零冲突。

### 5.3 B3 写手 Agent（Writer）｜ **P0**

- **职责**：逐章/逐场完成正文写作。
- **每章固定闭环**（工具调用顺序严格）：
  1. `加载上下文`：前情摘要、活跃伏笔、相关角色快照、文风规则、历史相似章节推荐；
  2. `回读前文`：抽取最近 1–2 章原文找回语气与节奏；
  3. `规划本章`：本章目标、冲突、情绪曲线、章末钩子；
  4. `写作正文`：按字数区间成稿；
  5. `一致性自检`：对照事实层检查（必须在成稿后执行）；
  6. `提交终稿`：返回结构化事实增量（新登场角色、伏笔埋设/回收、时间推进、地点变更），写入 C 层。
- **验收**：单章 3000–5000 字端到端 ≤ 3 分钟；事实增量提取准确率 ≥ 98%。

### 5.4 B4 评审主编 Agent（Editor-in-Chief）｜ P1（小说线 P0.5，随 MVP 后首个迭代交付；剧本线 P0）

- **职责**：站在主编视角做跨章/跨场的弧级评审，与写手的自检分离。
- **评审维度**：
  - 结构：节奏雷同检测（连续章节结构重复）、水文/注水检测、详略失当；
  - 人物：弧光完整性、动机合理性、声音辨识度（去掉名字能否分辨是谁在说话）；
  - 情节：逻辑链完整性、巧合滥用、冲突强度曲线；
  - 商业：钩子密度、爽点/泪点分布、付费卡点质量（网文）；悬念结构、反转有效性（剧本）。
- **输出**：裁定（通过/局部重写/整章重写）+ 问题清单（定位到段落）+ 可执行修改建议 + 影响范围评估。
- **验收**：检出问题的采纳率（人类编辑认可）≥ 70%；误报率 ≤ 20%。

### 5.5 B5 剧本师 Agent（Scriptwriter）｜ **P0（剧本线）**

- **职责**：剧本专项创作，等价于小说线的写手，但按剧本文体工作。
- **能力明细**：
  - 分幕/分场大纲生成（三幕式、起承转合、英雄之旅等结构模型可选）；
  - 标准格式剧本输出：场景头（内/外景·地点·日/夜）、动作描述、角色名、对白、括注；
  - 对白专项：按角色声音档案生成差异化对白，潜台词控制；
  - 节拍表（Beat Sheet）管理：每个节拍的功能标注与时长估算；
  - 场景功能自检：每场必须有明确的戏剧功能（推进/转折/揭示/铺垫），无功能场景告警。
- **验收**：输出 100% 可解析为标准剧本结构；场景功能标注覆盖率 100%。

### 5.6 B6 改编师 Agent（Adaptor）｜ P1

- **职责**：小说 ↔ 剧本双向转换（详见 F 层）。
- **核心能力**：主线提炼、视角转换（叙述→行动+对白）、取舍决策（合并次要人物/删减支线）并输出**改编说明文档**（每一处取舍的理由）。
- **验收**：改编方案中主要人物与主线事件保真率 100%；取舍说明完整可查。

### 5.7 B7 调研员 Agent（Researcher）｜ P2

- **职责**：联网检索支撑创作真实性与时效性。
- **场景**：历史/职业/地域细节考证；题材市场热度分析；竞品作品卖点拆解。
- **输出**：带引用的资料卡，自动归档入设定集。
- **验收**：资料卡事实性错误率 ≤ 1%（抽检）。

### 5.8 B8 合规官 Agent（Compliance）｜ **P0**

- **职责**：全产物的红线检测与改写建议（详见 I 层）。
- **介入点**：大纲确认时（前置拦截题材风险）、每章/每场提交时、成稿交付前（全量扫描）。
- **验收**：红线内容漏检率 ≈ 0（对抗样本集测试）；误伤率 ≤ 3%。

### 5.9 B9 润色师 Agent（Polisher）｜ P1

- **职责**：交付前的文字精修，与创作分离。
- **能力**：语病/错别字/标点修正；句式节奏优化；口头禅与重复用词消解；去 AI 味（消解模板化表达、过度排比、空泛抒情）。
- **约束**：只改表达，不改情节与设定；所有修改留痕可比对。
- **验收**：润色后人工抽评「可直接交付」率 ≥ 80%。

### 5.10 Agent 协同协议（基础设施）｜ **P0**

- 统一消息总线与任务队列；Agent 间只通过结构化事实与产物句柄通信，不共享裸上下文；
- 所有 Agent 调用留痕（输入/输出/耗时/token 成本），支持全链路回放与归因；
- 人类介入事件作为一等公民进入调度：修改某章 → 自动标记受影响下游 → 按需重跑。

### 14.2 KANO 模型分类

| 类型 | 定义 | 功能 | 策略 |
|---|---|---|---|
| 基本型 | 缺失即流失，有了不加分 | 一致性（C 层+G1）、续写（D7）、标准格式（E5）、导出（H14）、合规（I 层）、版本管理（H10） | 必须 P0，做到行业最好但不作为宣传卖点 |

### 14.3 优先级决策模型

每个功能的优先级由以下公式辅助判定，并经产品委员会评审：

```
优先级得分 = (用户价值 × 使用频率 × 差异化系数) / (实现成本 × 技术风险)
```

**硬性规则（高于公式）**：
1. **阻断核心闭环 = 自动 P0**：若功能缺失导致「一句话→成稿」主链路断裂（如 B1/C5/H14），无论得分直接 P0。
2. **合规 = 自动 P0**：I 层全部功能不受成本约束前置。
3. **验收不可量化 = 降级**：无法定义客观验收标准的功能不得进入 P0（避免「做了很多但不知道好不好」）。
4. **单点依赖过多 = 拆期**：依赖 3 个以上未交付功能的功能，顺延至下一里程碑。

**差异化系数取值**：通用大模型免费可做的事 ×0.5（如简单润色）；垂直深水区 ×2.0（如伏笔账本、剧本场景功能校验）；行业空白 ×3.0（如改编说明文档、双文体对照）。

### 14.4 我们不做什么的再确认（防范围蔓延）

- 不做通用聊天助手：所有入口必须落在「作品」实体上；
- 不做视频/音频生成：剧本交付到标准文件为止；
- 不做低幼化「一键成书玩具」：全自动模式必须产出经得起 G3 体检的稿件，宁可限制题材范围也不放水质量。

## 16. 深度分析：指标体系与质量评估机制

### 16.1 北极星指标

> **周均可交付字数（Weekly Acceptable Words, WAW）**：一周内用户接受（未做结构性重写，修改量 ≤ 20%）并保留在作品中的 AI 生成字数。

选它的理由：同时约束**质量**（不被接受的字数不计）、**产能**（字数规模）、**信任**（作者愿意留用），且无法通过刷低质量字数作弊。

### 16.2 分层指标树

| 层 | 指标 | 定义 | M1 目标 | M4 目标 |
|---|---|---|---|---|
| 北极星 | WAW | 周均可交付字数/活跃用户 | 8,000 字 | 30,000 字 |
| 获取 | 注册→首作品转化率 | 注册后 24h 内创建作品比例 | 40% | 55% |
| 激活 | 蓝图确认率 | B2 蓝图被用户直接确认比例 | 60% | 75% |
| 留存 | 4 周留存 | 首章生成后第 4 周仍活跃 | 25% | 40% |
| 质量 | 一致性自检通过率 | 章级 G1 一次通过比例 | 90% | 95% |
| 质量 | 评审采纳率 | 人类认可 B4 意见比例 | 60% | 75% |
| 质量 | 人工干预率 | 全自动初稿被修改字数占比 | ≤25% | ≤15% |
| 商业 | 免费→付费转化 | 月度 | 3% | 8% |
| 成本 | 千次可交付字成本 | 推理成本/WAW | 基线建立 | 降 40% |

### 16.3 质量评估机制（三轨制）

1. **自动化基准集**：维护 50 个标准测试作品（覆盖各题材与文体），每次模型/Prompt 变更全量回归：一致性、结构合规、伏笔回收、红线漏检均为自动化断言；
2. **盲评面板**：签约 10–20 名资深编辑/编剧组成评审团，定期对 AI 产出与人类作品混排盲评，跟踪「无法分辨率」与偏好率；
3. **线上信号回流**：用户的「换一版」点击率、段落删除率、评审驳回率自动汇入质量看板，按题材切片定位弱项。

| 编号 | 失败模式 | 检测方式 | 降级策略 | 用户呈现 |

**设计总则**：任何自动化失败都不允许「静默产生错误内容」——要么自动修复，要么显式升级给人类裁决，二者必居其一。

## 24. M0：小说闭环收敛版本

### 24.1 M0 目标与边界

**目标用户**：已经有题材想法、愿意按章审阅的个人中文小说作者。  
**核心任务**：作者能从主题创建一个 10 章作品，逐章生成、审阅、定稿、修订并导出；任一中断或事实争议都不会静默破坏已确认内容。  
**产品承诺**：AI 给出可编辑草稿和明确问题，不替作者在事实冲突或重大剧情改动上做不可逆裁决。

**当前实现位置**：M0-A 已完成“新故事表单→NestJS 认证 API→NestJS 持久化 Project/Run→Python 异步生成架构/目录→NestJS 同步状态/产物→Web 轮询进度与预览结果”。M0-B 已补齐最小作品库、蓝图确认和章节计划入口（仅返回当前作者项目、显示最近一次任务状态、可重开、可保存蓝图草稿、可确认当前蓝图并写入项目指针；可为任一章节保存结构化计划、确认计划并保留修订版本）。M0-04 已完成草稿生成、历史恢复和版本比较：仅当当前蓝图和本章计划都已确认时，作者可输入一次性附加要求并生成草稿；NestJS 创建 `CHAPTER_DRAFT` Run，Python 接收不可变蓝图/章纲/指令快照并回传正文，NestJS 持久化不可变 `ChapterRevision`。Web 可查看只读草稿快照和历史版本，通过章节当前草稿指针恢复任一历史版本，并查看两个版本间的逐行新增、删除和未改动内容。M0-05 已完成事实建议与裁决：Python Runtime 在草稿生成后从正文提取带证据和置信度的新增事实建议，NestJS 以 Run 快照幂等落库；章节修订下的事实建议可被提交、接受、编辑后接受或拒绝，作者可从已确认事实中选择更新或移除目标，只有接受结果才在事务中写入确认事实层。M0-06a 已完成最小定稿事务：只有当前草稿且本修订没有待裁决事实时，NestJS 才在同一事务中标记修订定稿、替换章节定稿指针并创建定稿记录；摘要和检索索引均以可见的待处理状态持久化，不会被伪装为已完成。当前尚未实现摘要/索引执行器、跨阶段版本回滚和导出。后续实现不得重做或旁路现有 Studio API 与 Python Runtime。

M0 不新建账号体系（复用现有认证基础设施即可），且明确不做云端多人协作、剧本、小说改编、自动联网调研、模型训练/微调、商业合规审查、DOCX/Final Draft 导出，以及无人工确认的整书批量定稿。批量生成如被保留，仅能生成草稿，不可绕过质量闸和人工确认。

### 24.2 M0 主流程

```text
创建作品
  -> 生成/编辑蓝图
  -> 确认目录
  -> 生成章节计划
  -> 生成草稿
  -> 作者编辑或接受
  -> 提取事实增量
  -> 作者确认事实增量
  -> 定稿、生成快照、更新摘要和检索索引
  -> 进入下一章或回滚/修订
```

| 阶段 | 作者动作 | 系统必须完成 | 完成定义 |
|---|---|---|---|
| 创建 | 输入主题、类型、目标章节数、单章字数与创作指导 | 创建项目、固定模型配置快照、初始化目录结构 | 项目可重开，配置不因全局设置变更而漂移 |
| 蓝图 | 查看并编辑架构与角色初稿 | 保存蓝图版本，生成初始角色事实条目 | 作者明确点击“确认蓝图”后才能生成目录 |
| 目录 | 生成、编辑章节标题与目标 | 记录目录版本和每章计划状态 | 被修改章节及后续章节标记为待重新规划 |
| 草稿 | 选择章节、审阅并可编辑提示词后生成 | 保存请求摘要、模型配置、输出和检索来源 | 草稿不会覆盖任何已定稿版本 |
| 事实确认 | 审阅角色/时间/设定/伏笔变更建议 | 对每项提供接受、拒绝、编辑三种操作 | 未裁决事实不能写入已确认事实层 |
| 定稿 | 确认章节内容与事实变化 | 建立章节快照、更新摘要、当前事实层和索引 | 所有写入成功后任务才进入 `finalized` |
| 复核与导出 | 查看问题、回滚或导出 | 输出带章节顺序的 txt/md 及质量报告简版 | 导出的版本、报告和事实快照具有相同版本号 |

### 24.4 M0-04 实施记录与剩余拆解

已交付的最小闭环：`POST /studio/projects/:projectId/chapters/:chapterNumber/drafts` 只接受已确认且绑定当前蓝图的章节计划；每次请求新建独立 Run，保存作者附加要求和运行时模型配置，Python 在 `inputs/<run-id>/request.json` 保存蓝图、章纲和指令快照。运行成功后，NestJS 以 Run ID 创建不可变 `ChapterRevision`，记录正文哈希、字数、提示词摘要、模型配置和来源计划；同一 Run 的重复同步不会产生第二份修订。Web 的草稿正文为只读快照，避免把草稿编辑误认为定稿。

后续按以下顺序推进，避免在没有事实裁决和事务边界时开放“定稿”按钮：

1. M0-05c 已完成：Python 输出并规范化 `confidence`（0–1），NestJS 保存并回传该字段；工作台展示置信度，且更新/移除操作必须从已确认事实选择目标。仍需在真实作者样本中评估提取准确率与置信度校准。草稿比较已使用有界逐行差异算法，超过安全行数时退化为整段替换，避免拖垮 API。
2. M0-06a 已完成：`finalize` API 只接受当前草稿且没有待裁决事实的修订，在事务内更新不可变修订状态、定稿指针和定稿记录；摘要、检索索引以 `pending` 状态显式记录。M0-06b：接入 Python 摘要/索引执行器与可恢复任务，完成后回写状态；失败时保留草稿和可恢复 Run。
3. M0-07/M0-08：写入结构化审校问题、处理裁决，并把蓝图/章节回滚实现为新指针而非删除历史。

## 25. 领域对象、产物与数据契约

### 25.1 领域对象

M0 不要求一次性替换所有 TXT 文件，但要求新增结构化索引作为产品级可信源；原有文本文件是可读产物和兼容层。NestJS + PostgreSQL 保存 `Project`、`Run`、`Revision`、`Fact` 和授权/审计记录的权威版本；Python 只保存与某次运行关联的执行工作区、检索索引和大文本产物。所有对象都必须带 `id`、`version`、`created_at`、`updated_at`、`source` 和 `schema_version`；跨服务产物还必须记录 `run_id`、内容摘要和来源版本。

| 对象 | 关键字段 | 所有者 | 说明 |
|---|---|---|---|
| `Project` | `id`、标题、类型、目标章节数、模型配置快照、当前版本指针 | 作者 | 一部作品的根对象 |
| `Blueprint` | 主题、类型、叙事视角、世界观、角色、主线、目录版本 | 作者确认，AI 提议 | 对应现有 `Novel_architecture.txt`，但不再只存自由文本 |
| `ChapterPlan` | 章节序号、标题、目标、冲突、出场人物、地点、时间、伏笔、钩子 | 作者确认，AI 提议 | 对应现有 `Novel_directory.txt` 的可执行子集 |
| `ChapterRevision` | 章节 ID、父版本、正文、来源草稿、状态、字数、审校结果 | 作者 | 所有草稿和定稿均不可变 |
| `Fact` | 类型、主体、属性、值、生效章节、置信度、来源锚点、状态 | 作者确认 | 类型至少包含角色、设定、时间事件、物品、伏笔 |
| `FactChange` | 操作、目标事实、前值、后值、建议理由、来源章节、裁决 | AI 提议，作者裁决 | 是事实层写入的唯一入口 |
| `ReviewFinding` | 规则、严重度、对象、证据、建议、状态、裁决记录 | 审校器 | 取代只写入日志的审校文本 |
| `Run` | 任务类型、输入快照、模型配置、状态、重试、耗时、错误、产物 ID | 系统 | 支撑恢复、成本统计与问题复现 |

### 25.2 Python 执行工作区与兼容策略

```text
<project-root>/
  inputs/<run-id>/             # Nest 下发的不可变执行输入
  outputs/<run-id>/            # 架构、目录、章节、审校等原始产物
  checkpoints/<run-id>/        # 可恢复的 Python 执行检查点
  legacy/                      # 现有 TXT 文件的只读兼容镜像
  vectorstore/                 # 现有 Chroma 检索库
```

上图是 Python 服务的执行目录，**不是产品主数据库**。Python 返回产物内容或受保护的产物引用与摘要；NestJS 在事务中把已接受的结果写入领域记录并生成审计事件。迁移原则：首次导入旧作品时，Python 读取 `Novel_architecture.txt`、`Novel_directory.txt`、`character_state.txt`、`global_summary.txt` 和 `chapters/chapter_N.txt` 生成预览，NestJS 创建“待确认”项目快照；原文件不被删除或覆盖。只有作者确认迁移预览后，NestJS 才创建结构化事实和当前版本指针。

### 25.3 事实与检索的职责边界

1. 已确认的 `Fact` 是生成和审校的唯一硬约束；冲突时必须阻断定稿或要求人工裁决。
2. 章节计划、近章原文、摘要和向量召回是软上下文，用于补足表达与细节，不得自动改写事实。
3. 每条事实和审校问题必须能回链到章节版本与文本锚点；仅“模型认为”不足以构成事实。
4. 嵌入失败不能阻断定稿，但必须在任务记录中标记“检索索引待补建”，下次启动可补偿执行。

## 26. 核心状态机与人工裁决机制

### 26.1 章节状态机

```text
planned -> drafting -> draft_ready -> reviewing -> fact_pending
                                      |                  |
                                      v                  v
                                   failed <--------- fact_rejected
                                                         |
                                                         v
                                                    finalizing -> finalized
                                                                     |
                                                                     v
                                                               superseded
```

| 状态 | 进入条件 | 允许动作 | 禁止动作 |
|---|---|---|---|
| `planned` | 章节计划已确认 | 生成草稿、编辑计划 | 作为定稿导出 |
| `drafting` | 已创建 `Run` | 取消、等待、查看运行日志 | 并发启动同章定稿 |
| `draft_ready` | 草稿文本及其输入快照已保存 | 编辑、生成新草稿、发起审校 | 覆盖历史草稿 |
| `reviewing` | 已开始规则校验或 LLM 审校 | 查看问题、取消低优先级审校 | 直接写入事实层 |
| `fact_pending` | 事实变更建议已生成 | 接受、编辑、拒绝每个变更 | 自动定稿 |
| `finalizing` | 正文和必需事实均已确认 | 等待或从检查点恢复 | 修改正文或事实 |
| `finalized` | 快照、事实、摘要和任务日志均已提交 | 导出、创建后续计划、发起修订 | 原地覆盖内容 |
| `superseded` | 新定稿成为当前版本 | 查看、比较、恢复为新当前版本 | 作为默认生成上下文 |
| `failed` | 运行不可自动恢复 | 重试、查看错误、从检查点恢复 | 伪装为成功 |

### 26.2 质量闸与裁决规则

| 闸门 | 触发时机 | 阻断条件 | 作者选项 |
|---|---|---|---|
| 输入完整性 | 生成前 | 无蓝图/章节计划/模型配置快照 | 补全、返回编辑 |
| 硬事实校验 | 定稿前 | 角色状态、时间、地点、物品归属等已确认事实冲突 | 修改正文、编辑事实、标记为“有意改设定”并生成变更 |
| 软质量审校 | 草稿完成后 | 节奏、重复、钩子、表达问题 | 采纳、忽略、再生成；默认不阻断 |
| 事实增量确认 | 定稿前 | 新增或修改事实未裁决 | 接受、编辑、拒绝 |
| 事务完整性 | 定稿时 | 任一必须写入项失败 | 自动回滚或保留检查点，禁止显示“定稿成功” |
| 导出检查 | 导出前 | 含未定稿章节或未解决 P0 问题 | 仅导出已确认章节，或要求明确强制导出理由 |

人工裁决不是异常路径。作者的“拒绝审校”“修改事实”“有意改设定”和“强制导出”都要写入 `Decision` 记录，包含原因、操作者、时间、影响范围和后续处理状态。该记录既用于回溯，也用于后续评估审校误报率，不能直接作为训练数据使用。

## 27. 现有工程的迁移与兼容方案

### 27.1 分层改造顺序

| 顺序 | 改造内容 | 复用现有模块 | 完成后获得的产品能力 |
|---|---|---|---|
| 1 | 在 NestJS 建立 Project、Run、Blueprint、ChapterPlan、Revision、Fact 的持久模型和资源归属 | `apps/api/src/modules/studio/`、Prisma/DB Service | 产品主数据可查询、授权、审计和恢复 |
| 2 | 扩展公开 Studio 契约与内部 Python Runtime 契约 | `packages/contracts/`、`novel-runtime.client.ts`、`backend/runtime/api.py` | 浏览器只见稳定 API；Python 只接收受控执行输入 |
| 3 | 为架构、目录、草稿、定稿封装持久 `Run`、阶段事件和检查点 | `backend/runtime/engine.py`、NestJS 任务服务 | 可恢复、可定位失败步骤，不依赖 Python 内存字典 |
| 4 | 将角色状态/摘要生成改为“Python 提议事实变化→Nest 持久化→作者确认提交” | `backend/novel_generator/finalization.py`、提示词定义 | 事实更新可审阅、可回滚 |
| 5 | 将一致性审校输出解析为 `ReviewFinding`，由 NestJS 保存裁决 | `backend/consistency_checker.py` | 问题可展示、筛选、裁决和统计 |
| 6 | 将向量库加上章节版本与来源元数据 | `backend/novel_generator/vectorstore_utils.py` | 检索结果可追溯且不会混入废弃版本 |
| 7 | 在 Web 应用中实现作品首页、版本/事实/问题面板 | `apps/web/app/`、`apps/web/components/`、`packages/ui/` | 用户不再依赖文件名和日志理解系统状态 |

### 27.2 兼容性验收

1. 旧作品迁移后，原 TXT 文件内容字节不变，章节顺序和正文不丢失。
2. 迁移前后的“当前章节”“目标字数”“模型选择”和已定稿章节数可对照。
3. 任一新版本均可导出为与旧版兼容的 `Novel_architecture.txt`、`Novel_directory.txt`、`character_state.txt`、`global_summary.txt` 和 `chapters/chapter_N.txt` 镜像，直至旧界面下线。
4. 向量库重建失败不影响作品打开；系统必须提供重建入口和明确状态。
5. 现有单元测试保持通过，并为项目迁移、章节状态迁移、定稿事务和回滚各新增至少一个回归用例。

## 30. 设计研究与体验目标

### 30.1 当前证据与待验证假设

当前存在三类工程/文档证据：遗留原型已经保留“作者编辑提示词”“定稿前人工确认”“角色状态与摘要更新”三个关键动作；原 PRD 将大纲、初稿产能和一致性列为最高痛点；Web 项目已具备适合承载复杂工作台的应用壳与组件基础。它们只能支持**设计假设**，不能替代真实用户研究。高保真设计与功能扩面前，必须完成下列验证。

| 编号 | 假设 | 需要验证的信号 | 失败后的调整 |
|---|---|---|---|
| H-01 | 作者愿意在生成前确认章节计划，以换取更少的返工 | 5 位目标作者中至少 4 位在无引导下查看并修改计划 | 将计划压缩为“本章目标 + 人物 + 钩子”三项，其他内容渐进展开 |
| H-02 | 作者能理解“事实增量”并愿意裁决，而不会感到被配置表打断 | 80% 参与者能正确完成接受、编辑或拒绝一次事实变更 | 改为自然语言解释 + 高亮原文锚点，隐藏低价值字段 |
| H-03 | “草稿与定稿分离”能让作者更放心尝试 | 80% 参与者能在 90 秒内生成第二个草稿并恢复首稿 | 把版本入口前置到编辑器工具栏，减少版本术语 |
| H-04 | 三栏工作台不会在写作时形成认知负担 | 80% 参与者能在 2 分钟内找到章节目标、活跃事实和问题 | 默认收起右栏；按任务显示单一上下文卡片 |

### 30.2 M0 体验原则

1. **先创作，后管理**：正文编辑区始终是主要视觉焦点；事实、任务和报告按需出现，不能抢占写作空间。
2. **每次 AI 行为可见且可撤销**：生成前显示将使用的章节计划和上下文摘要；生成后保留草稿来源；定稿后可恢复。
3. **把系统语言翻译成作者语言**：界面优先使用“本章目标、已确认设定、待确认变化、问题”，不以“Agent、向量、schema”作为主文案。
4. **风险分级，不制造噪声**：只有会导致事实冲突、数据丢失或导出不完整的问题阻断操作；表达建议默认可忽略。
5. **渐进展开**：新作者完成“创建作品→生成蓝图→写第一章”不超过一个主页面和一个确认面板；高级配置在二级入口。

### 30.3 关键旅程地图：完成第一章

| 阶段 | 创建作品 | 确认蓝图 | 生成草稿 | 裁决事实 | 定稿与继续 |
|---|---|---|---|---|---|
| 作者动作 | 填写主题和创作方向 | 修改不满意的设定/目录 | 查看计划，生成并编辑正文 | 处理角色、地点、时间等变化 | 确认保存并进入下一章 |
| 主要触点 | 创建向导 | 蓝图页 | 创作工作台 | 右侧抽屉 | 顶部状态与章节导航 |
| 预期感受 | 轻松开始 | 有掌控感 | 专注、被支持 | 确信而非被打断 | 安心继续 |
| 主要风险 | 表单过长 | 产物过多难以判断 | 等待时不知系统在做什么 | 术语生硬、变化太多 | 不清楚是否真的保存成功 |
| 设计机会 | 用示例与默认值降低空白感 | 只展示需决策项 | 流式正文 + 可取消任务 | 原文锚点、批量接受与逐条编辑 | 明确版本号、保存时间和下一步 |

## 31. 信息架构与导航模型

### 31.1 M0 站点地图

```text
应用壳
├── 作品库
│   ├── 新建作品
│   ├── 导入遗留作品
│   └── 最近打开 / 状态筛选
├── 作品工作台
│   ├── 概览（进度、待处理、最近章节）
│   ├── 蓝图（作品设定、角色、目录）
│   ├── 创作（章节计划、正文、上下文、任务）
│   ├── 事实与问题（已确认事实、待确认变化、审校问题）
│   └── 版本与导出（章节版本、恢复、txt/md）
└── 偏好设置（模型配置、外观、快捷键）
```

导航采用两层：全局侧栏只放“作品库、当前作品、设置”；进入作品后使用作品级侧栏承载“概览、蓝图、创作、事实与问题、版本与导出”。禁止把“生成架构、生成目录、生成草稿、定稿”做成孤立的四个顶级页面，避免用户将流程误解为一次性线性向导。

### 31.2 信息架构验证任务

在视觉设计开始前，对 5 位目标作者进行 10 分钟闭合卡片分类或树测试，要求其定位以下任务：修改角色设定、生成下一章、查看某个冲突、恢复昨天的版本、导出已定稿内容。每项定位成功率应不低于 80%；低于阈值时先调整导航命名和层级，再进入中保真原型。

## 32. M0 低保真产品原型

原型以 1440 px 桌面视口为主，覆盖完整快乐路径与“定稿失败可恢复”异常路径。移动端仅支持作品浏览、问题裁决和轻量编辑，不作为 M0 的主写作入口。

### 32.1 作品库与创建向导

```text
┌──────────────────────────── 作品库 ────────────────────────────┐
│ 瀚霖创作引擎                         [导入作品] [新建作品 +]   │
├───────────────┬────────────────────────────────────────────────┤
│ 所有作品       │ 继续创作                                        │
│ 最近打开       │  ┌──────────────────────────────────────────┐  │
│ 待处理问题     │  │ 《边城烬火》  第 3 / 10 章  ·  草稿待确认 │  │
│ 已归档         │  │ 上次编辑 12 分钟前              [继续]   │  │
│               │  └──────────────────────────────────────────┘  │
│               │ 你的作品                                        │
│               │  [作品卡：标题、进度、最后活动、风险状态]       │
└───────────────┴────────────────────────────────────────────────┘

新建作品（Sheet，3 步）：
  1. 故事方向：标题（可选）、主题、类型、创作方向
  2. 写作规模：目标章节数、每章字数、叙事视角
  3. 确认：模型配置摘要、保存位置、创建并生成蓝图
```

创建向导默认使用可编辑示例，必填字段仅为“主题”和“类型”。每一步显示当前完成状态；关闭时保存为未发布草稿。点击最终操作后，创建项目与蓝图任务同时启动，用户进入蓝图页而不是停留在加载弹窗。

### 32.2 创作工作台：主要原型

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 作品库 / 边城烬火 / 第 3 章                    已保存 10:42   [导出] [⋯] │
├───────────────┬──────────────────────────────────────┬─────────────────────┤
│ 作品导航       │ 第 3 章  雪夜来信                    │ 本章上下文          │
│ 概览           │ 目标：主角得知密信，决定离城          │ [章节计划]          │
│ 蓝图           │ [生成草稿] [比较版本] [定稿]          │ 人物 2   地点 1     │
│ 创作           ├──────────────────────────────────────┤ 待确认变化 2       │
│  ├ 第 1 章 ✓   │                                      │ ─────────────────   │
│  ├ 第 2 章 ✓   │          正文可编辑区域               │ 问题                │
│  └ 第 3 章 ●   │                                      │ ! 时间线：1 个      │
│ 事实与问题  2  │                                      │ [查看详情]          │
│ 版本与导出     ├──────────────────────────────────────┤                     │
│                │ 草稿 v2 · 由“章节计划 v3”生成         │                     │
│                │ [撤销] [重做]              1,842 字   │                     │
└───────────────┴──────────────────────────────────────┴─────────────────────┘
```

布局规则：左侧作品导航固定 240 px；右侧上下文栏默认 320 px，可收起；正文列最小 640 px、最大 860 px；编辑器顶部操作区固定但不遮挡文本。正文是唯一允许连续长滚动的主区域，其他面板独立滚动。章节状态使用图标、文本与颜色三重表达，不能只靠颜色区分。

### 32.3 事实增量裁决抽屉

```text
┌────────────────────── 待确认变化 2 ──────────────────────┐
│ 第 3 章 · 草稿 v2                                         │
├───────────────────────────────────────────────────────────┤
│ 角色状态  ·  林砚                                          │
│ “受伤” → “左臂擦伤，行动受限”                              │
│ 原文：他按住左臂，血顺着袖口滴下。                         │
│ [接受]  [编辑变化]  [不记录]                               │
├───────────────────────────────────────────────────────────┤
│ 伏笔  ·  新增“密信落款”                                    │
│ 原文：蜡封上只有一个残缺的青鸟印。                         │
│ [接受]  [编辑变化]  [不记录]                               │
├───────────────────────────────────────────────────────────┤
│ 0 项待处理                         [保存为草稿] [确认并定稿] │
└───────────────────────────────────────────────────────────┘
```

抽屉从右侧滑出，保留正文可见。默认逐项裁决；当所有变更都来自同一低风险类别时，才显示“接受全部”。“确认并定稿”在仍有待裁决项目、P0 冲突或正文未保存时禁用，并以内联原因说明禁用原因。

### 32.4 失败恢复状态

```text
┌──────────────────────── 定稿未完成 ────────────────────────┐
│ 已保存正文和事实裁决；摘要更新未完成。                      │
│                                                              │
│ 当前版本：草稿 v2       恢复点：定稿事务 #run_8f2            │
│ [继续完成定稿]  [保留为草稿]  [查看技术详情]                │
│                                                              │
│ 不会丢失已保存内容。                                         │
└──────────────────────────────────────────────────────────────┘
```

异常状态必须在章节顶部和任务中心同时可见；禁止只写日志或只使用短暂 Toast。用户可以安全离开并在下次打开时继续处理。

## 33. 关键交互与状态规格

### 33.1 主操作交互

| 场景 | 触发与反馈 | 成功状态 | 失败/取消状态 |
|---|---|---|---|
| 创建项目 | 点击“创建并生成蓝图”后立即进入作品页，顶部展示任务进度 | 生成蓝图初稿，导航解锁“蓝图” | 创建失败保留表单草稿；可重试，不生成空项目 |
| 编辑蓝图 | 字段失焦后自动保存，顶部显示保存时间 | 新版本写入；受影响目录以“需检查”标记 | 保存失败显示内联重试，不静默回退 |
| 生成草稿 | 先展开章节计划确认区；确认后开始任务，可取消 | 新草稿作为版本出现，编辑器切换但不删除前稿 | 失败保留输入和运行记录，提供重试/更换模型/返回编辑 |
| 直接编辑正文 | 750 ms 空闲后自动保存；离开页面前确保本地草稿已提交 | “已保存”显示具体时间 | 网络异常显示“仅本地草稿”，恢复后提示同步 |
| 发起定稿 | 先运行硬事实校验和事实增量提取，再打开裁决抽屉 | 事务完成后显示“已定稿 vN”，下一章变为可开始 | 任一写入失败进入恢复状态，绝不显示成功 |
| 回滚版本 | 从版本列表选择，先展示差异和影响范围，再二次确认 | 新建当前指针，原版本保留 | 取消后不改变当前版本 |
| 导出 | 选择 txt/md；预览将导出的章节和未解决风险 | 文件附带作品/版本元数据 | 有阻塞问题时只允许“导出已确认章节”或明确强制导出 |

### 33.2 微交互、加载与通知

1. 所有异步主操作使用按钮内 Loading 图标并禁用重复提交；长任务同时写入可关闭的任务中心。
2. 文本流式生成时，正文显示增量内容、已生成字数、停止按钮和“草稿未保存”的状态；停止后保留已生成文本作为新草稿。
3. 保存成功使用静态状态文本，不以连续 Toast 打断创作；只有失败、恢复成功、导出完成使用可关闭 Toast。
4. 删除草稿、清空向量索引、强制导出、恢复版本均为破坏性操作：使用危险按钮、影响范围和二次确认，默认焦点放在取消操作。
5. 所有图标按钮必须有 Tooltip；使用 Lucide 图标，不自绘 SVG。图标用于关闭、收起、更多操作、版本比较等高频工具；文字按钮仅用于生成、定稿、导出等明确命令。
6. Web 端的轮询或 SSE 只订阅 NestJS 公开任务端点；Python 运行时进度由 NestJS 聚合、持久化后再下发，前端不得知道 Python 地址、内部任务密钥或模型配置。

### 33.3 键盘与焦点

| 操作 | 桌面快捷键 | 焦点/读屏要求 |
|---|---|---|
| 保存草稿 | `Cmd/Ctrl + S` | 保存结果通过 `aria-live` 简短播报 |
| 打开命令面板 | `Cmd/Ctrl + K` | 打开后焦点进入搜索框，Esc 返回原位置 |
| 切换右侧上下文栏 | `Cmd/Ctrl + .` | 收起后焦点不丢失，按钮更新 `aria-expanded` |
| 生成草稿 | `Cmd/Ctrl + Enter` | 仅在计划已确认且编辑器非 IME 组合输入时生效 |
| 打开问题面板 | `Cmd/Ctrl + Shift + P` | 焦点跳转到首个未解决问题 |

### 34.3 无障碍与响应式门槛

1. 所有文本与背景、交互控件与背景的对比度至少 4.5:1；状态颜色必须同时配合图标和文字。
2. 键盘可完成创建、生成、编辑、裁决、定稿、回滚和导出；焦点顺序符合视觉顺序，焦点环始终可见。
3. Sheet/Dialog 打开后焦点锁定，关闭后回到触发元素；异步任务、保存和错误使用适度 `aria-live` 播报。
4. 桌面主写作体验最低宽度为 1024 px；1024–1279 px 自动收起右栏；小于 768 px 仅提供阅读、事实裁决和轻量编辑，生成与复杂版本比较引导用户切换桌面设备。
5. 交互控件最小点击区域 40 × 40 px；不得将仅悬停才可见的操作作为唯一入口。

## 35. 原型验证与可用性测试

### 35.1 测试计划

| 项目 | 设计 |
|---|---|
| 参与者 | 5–8 名中文小说作者；至少 3 名有连载/长篇创作经验，2 名使用过通用 AI 写作工具 |
| 原型 | 第 32 章中保真可点击原型，覆盖快乐路径和定稿失败恢复状态 |
| 方式 | 45 分钟远程主持测试；屏幕共享与口述思考；不在测试中解释产品术语 |
| 任务 1 | 从主题创建作品，修改蓝图中的一个角色设定，并进入第 1 章 |
| 任务 2 | 确认章节计划，生成第二份草稿，恢复第一份草稿 |
| 任务 3 | 处理一条角色状态变化和一条时间冲突，然后完成定稿 |
| 任务 4 | 模拟定稿失败后恢复任务，并导出已确认章节 |

### 35.2 成功标准与决策规则

| 指标 | 门槛 | 未达标处理 |
|---|---|---|
| 核心任务完成率 | 每项 ≥ 85% | 将阻塞点列为 P0 体验缺陷，修正后复测 |
| 章节计划确认 | ≥ 80% 参与者无需协助完成 | 简化计划字段和信息层级 |
| 事实裁决准确率 | ≥ 80% 能正确区分接受、编辑和拒绝 | 重写文案并强化原文锚点 |
| 定稿失败恢复 | ≥ 80% 能在 2 分钟内恢复或安全保留草稿 | 改进任务中心和恢复卡的可见性 |
| 平均 SUS | ≥ 68，目标 ≥ 80 | 优先解决严重度 1–2 的问题，再继续扩面 |
| 严重可用性问题 | 0 个未解决的严重度 1 问题 | 不进入开发冻结或内测 |

严重度定义：1 = 任务无法完成或可能丢失内容；2 = 可完成但需要帮助/明显绕路；3 = 困惑或效率问题；4 = 视觉润色。每轮测试后将观察、录屏时间戳、严重度、假设关联、建议改动和复测结果写入决策记录。
